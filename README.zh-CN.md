# Forward?

[English](README.md) | **简体中文**

**面向 AI Agent 的智能抗命（Intelligent Disobedience）。**

> **目的地由你决定，路线可以重新选择。**

现代 AI Agent 已经越来越擅长执行。

它们可以阅读代码、调用工具、修改文件、运行测试、撰写文档，并在很长的任务链路中持续推进。

这也让一种失败变得越来越昂贵：

**Agent 可能非常擅长执行，却一直在执行错误的路线。**

Forward? 是一个轻量级 Agent Skill。它给擅长执行的 Agent 增加一项额外责任：

**继续忠于用户的目标，但当现实已经不再支持当前路线时，重新判断这条路线是否还该继续。**

## 为什么叫 “Forward?”

这个想法来自导盲犬。

人决定要去哪里。

导盲犬负责眼前具体怎么走。

大多数时候，当主人发出 **“Forward”** 指令时，导盲犬会继续前进。

但 “Forward” 并不意味着：

> 无论发生什么都往前走。

如果有车正在经过，它可能停下来。

如果眼前的路不安全或被阻断，它可能拒绝执行这一步。

导盲犬拒绝的不是主人的目的地。

它拒绝的是一条已经不符合眼前现实的路线。

随后，它仍然会继续带主人前往同一个目的地。

这就是 **智能抗命（Intelligent Disobedience）**。

Forward? 把同样的责任交给 AI Agent：

> **必要时拒绝路线，但始终保留目的地。**

---

## 它改变了什么？

假设用户说：

> “可能是缓存过期了。重写缓存失效逻辑，把这个 Bug 修掉。”

一个执行能力很强的 Agent，完全可以立刻开始重写缓存层。

但用户真正的 **目标** 是修掉 Bug。

“缓存过期”只是一个假设。

“重写缓存失效逻辑”只是当前提出的一条路线。

它们不应该因为同时出现在一句指令里，就自动获得相同的权威性。

<p align="center">
  <img src="assets/what-changes.png" alt="普通 Agent 直接执行用户提出的路线，与 Forward? 检查路线是否仍然服务于目标的对比" width="100%" />
</p>

### 没有 Forward?

Agent 可能会把请求理解成：

```text
目标：修掉 Bug
      ↓
假设：缓存过期
      ↓
方法：重写缓存失效逻辑
      ↓
执行重写
```

于是，**路线悄悄变成了任务本身。**

### 使用 Forward?

Agent 会把目的地固定下来：

```text
目的地：修掉 Bug
        ↓
路线：真的是缓存过期吗？
        ↓
检查证据
        ↓
支持？ ───── 是 ────→ 继续
  │
  否
  ↓
改道
  ↓
修复真正原因
```

用户仍然拥有目标。

Agent 只是不会因为某个方法被说出口，就假装这个方法已经被现实证明是对的。

## 核心思想

Forward? 会把三件事分开。

### Destination — 目的地

用户真正想实现什么。

例如：

- 修掉 Bug；
- 发布功能；
- 完成上线；
- 产出准确的报告；
- 降低失败率。

### Route — 路线

当前打算怎么到达目的地。

一条路线可能是：

- 一个实现方案；
- 一个 Debug 假设；
- 一个临时 workaround；
- 一个架构选择；
- Agent 自己提出的方案；
- 已经执行了一段时间的步骤序列。

路线很有价值。

但路线也应该允许被修改。

### Road — 现实中的路况

路线必须经得住现实。

包括：

- 证据；
- 系统实际行为；
- 约束条件；
- 新发现的事实；
- 用户已经做出的决定；
- 成本和权衡；
- 到底有哪些事情真正被确认过。

Forward? 会反复问一个很小的问题：

> **基于我们现在的位置，以及现在已经知道的事实，继续走这条路线还合理吗？**

绝大多数时候，答案应该是：

> **合理。继续走。**

这一点很重要。

Forward? 不是为了让 Agent 变得犹豫。

它要解决的是：

**只在真正有必要时，Agent 才愿意改变路线。**

## Forward? 会怎么响应？

Forward? 有四种响应模式。

### PROCEED — 继续

当前路线仍然服务于目标。

那就继续。

不需要额外评论，也不需要仪式化验证。

### VERIFY — 验证

存在一个足以影响路线的重要不确定点，而且快速验证它可能改变后续选择。

先验证前提，再继续投入。

### CHALLENGE — 质疑

当前路线已经明显与目标、证据或约束发生冲突。

把冲突说清楚。

不要机械执行。

### REDIRECT — 改道

已经有一条更合理的路线，可以继续推进。

改变方法，但保留目的地。

真正重要的是：**质疑之后发生什么。**

任务不会因此停止。

Forward? 不是：

> “不做。”

而是：

> “不这么做。但我们还是继续去你要去的地方。”

## 安装

需要 **Node.js 18 或更高版本**。

安装器没有运行时依赖，也不会发送遥测数据。

```bash
npx forward-if install
```

Forward? 会检测支持的 Agent，并把同一份规范的 `SKILL.md` 安装到各客户端原生的 Skill 目录。

先预览会修改哪些位置：

```bash
npx forward-if install --dry-run
```

只安装到指定 Agent：

```bash
npx forward-if install --target codex
npx forward-if install --target claude
npx forward-if install --target gemini
```

安装到所有受支持的 Agent：

```bash
npx forward-if install --target all
```

安装到当前项目，而不是用户级目录：

```bash
npx forward-if install --scope project --project .
```

检查现有安装：

```bash
npx forward-if doctor
```

更新 Forward?：

```bash
npx forward-if update
```

移除由 Forward? 安装的文件：

```bash
npx forward-if uninstall
```

安装器会保存一份很小的 ownership 记录，因此 `doctor`、`update` 和 `uninstall` 只会管理由它自己安装的文件。

本地修改过的 Skill 文件不会被静默覆盖。

当需要用 `--force` 替换或移除冲突文件或本地修改过的 `SKILL.md` 时，安装器会先备份该文件。

平台发现机制和原生安装细节见 [平台支持](docs/platform-support.md)。

## 它不是“和用户唱反调”

Forward? 不是 Devil's Advocate 模式。

它不会要求 Agent 质疑每一条指令。

它不奖励犹豫。

它不会把所有任务都变成一场验证仪式。

它不会夺走用户对目标的决定权。

它也不会把“不确定”本身当成停止工作的理由。

绝大多数合理的指令，都应该直接继续执行。

> **不要主动寻找抗命的理由。看清眼前的路。**

---

## Agent 越强，这个问题反而越重要

弱 Agent 的失败往往是：它不会执行。

强 Agent 会以另一种方式失败。

它可能：

- 很早就押注一个看起来合理的解释；
- 当前提已经变弱时，仍不断给原路线打补丁；
- 因为已经投入了很多工作，而开始维护自己之前的实现；
- 把讨论过程悄悄升级成已经确认的决定；
- 把先前由 Agent 自己生成的内容，当成外部现实；
- 把局部步骤优化得越来越好，却逐渐偏离原始目标。

问题并不总是“推理不够”。

有时 Agent 正在 **错误的路线内部进行非常优秀的推理**。

> **想得更多，不等于重新检查前提。**

Forward? 增加的就是这个缺失的循环，而不是替代现代 Agent 已经拥有的强执行能力。

## 更多例子

### 用户的假设错了

**用户**

> API 可能是在超时。加十次重试吧。

普通执行路径可能立刻增加重试次数。

Forward? 会保留真正的目的地——提高可靠性——然后检查超时是否真的是根因。

如果失败实际上来自认证刷新时的竞态条件，增加重试只会制造更多请求，还可能掩盖真正的问题。

正确的响应不是：

> “我拒绝。”

而是：

> “我找到的失败原因不是超时，增加重试解决不了它。我会改为修复认证刷新竞态。”

---

### Agent 自己选的路线失效了

Agent 自己选择了一种实现方式，并连续几轮都在构建它。

后来，它发现现有系统已经提供了一套受支持的能力，可以让大部分自定义实现都变得没有必要。

之前的投入会影响切换成本。

但它 **不能证明原来的路线就是正确的**。

Forward? 允许 Agent 改道，而不是因为沉没成本继续维护旧路线。

---

### 讨论不等于已经做出决定

用户说：

> “有一些轻量级统计应该挺有用。”

此前 Agent 曾经提出五个具体指标。

这并不一定意味着：

> “用户已经批准这五个指标作为正式需求。”

Forward? 会尽量保留“用户真正决定了什么”和“Agent 只是提出了什么”之间的区别。

## 支持的 Agent

Forward? 以标准 `SKILL.md` Agent Skill 的形式发布。

规范 Skill 本身保持 provider-neutral。不同平台之间的差异由轻量安装适配层处理，而不是维护多份不同版本的 Skill。

当前安装器支持：

- Codex
- Claude Code
- Gemini CLI

已测试环境、发现机制、原生安装方式和当前限制见 [平台支持](docs/platform-support.md)。

## 评测

Forward? 是一个指令级的行为 Skill，不是模型权重改动。

因此，我们同时关注两个维度：

1. **Correction（纠偏）** —— 路线确实有问题时，Agent 会不会重新判断？
2. **Selectivity（选择性）** —— 路线本来就没问题时，Agent 能不能正常继续？

两者缺一不可。

一个从来不质疑任何路线的 Skill 没有意义。

一个什么都要质疑的 Skill 同样没有意义。

内部多轮 trajectory 评测中，我们观察到了 Forward? 在部分场景下能够重新打开已经变弱的路线，同时继续完成原始任务；也观察到了它在正常路线中不引入多余犹豫的 clean case。

目前的证据范围仍然刻意保持有限。

Forward? v0.1 **不宣称**在广泛 benchmark 上取得普遍优势，也不宣称已经解决所有长时程 Agent 行为问题。

当前一个已知限制出现在长对话中：模型有时会把用户对大方向的认可，进一步扩展成对 Agent 自己提出的更具体细节的认可。

这个问题仍然属于正在研究的部分，我们不会用一个 benchmark 分数把它藏起来。

完整的方法、案例、失败样本和诊断实验见：

- [Evaluation](docs/evaluation.md)
- [Known limitations](docs/known-limitations.md)

## 设计原则

Forward? 有意保持很小。

它的核心规则是：

- **默认继续前进。**
- **保留目的地。**
- **路线可以修改。**
- **依据现实，而不是依据对话惯性。**
- **过去的投入不是路线正确的证据。**
- **讨论不自动等于承诺。**
- **使用能够保护任务目标的最小必要纠偏。**
- **拒绝一条路线之后，继续推进目标。**

用户拥有目的地。

现实决定什么是真的、什么是可行的。

Agent 在被授权的范围内负责调查和执行。

> **用户可以覆盖选择，但不能覆盖现实。**

更完整的设计背景见 [Philosophy](docs/philosophy.md)。

---

## Forward? 不是什么

Forward? 不是：

- 安全拒绝框架；
- 安全边界；
- 强制执行运行时；
- 自主目标设定器；
- 对谄媚问题的通用解决方案；
- 每一步都必须执行的反思流程；
- 对优秀领域推理能力的替代品。

它只做一件刻意收窄的事情：

> **让一个已经很能执行的 Agent 忠于用户的目的地，而不是盲目忠于当前路线。**

## 状态

**v0.1.0 — 实验性、可用，并且刻意保持小。**

我们选择现在发布 Forward?，是因为它的核心思想已经足够值得进入真实 Agent 工作流测试，同时它的限制仍然保持可见并被明确记录。

项目后续会优先从真实使用和可复现评测中演进，而不是不断往 Skill 里堆更多规则。
